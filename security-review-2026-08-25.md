# Arcron: independent security and readiness review

_Date: 2026-08-25. Scope: full-repo breadth pass over `smart_contracts/`, `scripts/`, `web/`, `js/`, `docs/`, `specs/`, `tests/`, `deploy/`. Method: source reading (14 parallel review passes + independent spot-verification of all high/medium findings against the source). Nothing was executed: no tests, no chain, no recompile of keeper. "Confirmed" means confirmed by reading source; "reported" means found by a review pass and cited per-file but not independently re-verified._

## 1. Overview, in my own words

Arcron is two things, and the distinction matters for everything below. The **core** is a single Algorand app (`keeper`) that holds escrowed ALGO against registered "upkeeps" — parameterized app calls on a round cadence — and pays whoever executes a due upkeep, atomically, out of that upkeep's own escrow. Creators can cancel and recover escrow plus box MBR; nobody else can touch it; the deployer can rewrite the programs until a one-way `freeze()`. Around that core is a **supporting cast**: example target contracts (pulse, treasury, subscription, watchdog, deadman, embargo, rain), a reference keeper bot, a web console, a TS client library, governance/multisig tooling, and a large body of docs and specs.

My description matches the brief with one sharpening: the core has been hardened to the point where its own arithmetic, solvency, and ASA edge cases are the *strongest* part of the repo, while the risks that remain live almost entirely in the supporting cast — one example contract with a genuine money trap, a trust-communication layer (SECURITY.md, specs) that currently misdescribes the core, and off-chain tooling with stale/broken pieces. "The contract is fine but the system around it is rough" is the honest summary.

## 2. Security concerns, ordered by severity

**Can anyone lose money that was not theirs to lose?** In the **keeper contract itself**: no path found. Escrowed ALGO flows only to executing keepers (bounded fees) or back to the creator; the e2e finishing at exact minimum balance and the 1,008-execution soak corroborate this. The exceptions where someone *can* lose money: a **rain deployer** can steal every pot from participants (M1); a **deadman owner** loses their own escrow to the void (H1 — not to a third party, but total); a **console user following a phishing link** can escrow into an attacker's app (M7); and the **pre-freeze deployer** can rewrite the rules over everyone's escrow — a disclosed power, currently *mis*disclosed (H2). An ASA issuer with clawback/freeze powers can forfeit a creator's bonus on `cancel` — that's the issuer's power over its own asset, and the contract correctly refuses to let it hold ALGO hostage (`smart_contracts/keeper/contract.py:280-301`).

### High

**H1 — DeadMan: the default deploy path produces a switch whose beneficiary can never claim. Confirmed.** `smart_contracts/deadman/deploy_config.py:20-23` deploys the app without funding its base MBR. `arm` tracks the full deposit as escrow (`smart_contracts/deadman/contract.py:91`); `claim` pays the full tracked amount by inner payment (`contract.py:144`), which would leave the app account below the 100,000 µALGO base minimum balance — so the inner payment fails, every time, regardless of deposit size. The contract has no update or delete path, so the escrow is stranded permanently. The only thing that saves you is a manual pre-fund step that exists *only* in the demo (`scripts/deadman_demo.py:55-61`, sends 200,000 µALGO) — nothing in the contract, the deploy config, or the spec enforces or documents it. Who: any owner who deploys via the repo's own `deploy_config.py` — the standard AlgoKit path. Cost: the entire escrow. Fix is one line (fund MBR at deploy, or require/reserve MBR in `arm`). Not a box-struct change (deadman has no boxes), but the contract is immutable, so fixed instances get a new app id; already-armed instances are unfixable. It's an example contract, not shared infrastructure, so blast radius is "whoever copies it for real money."

**H2 — SECURITY.md's central claim is false for the live deployment. Confirmed.** `SECURITY.md:20-25`: "The contracts cannot be patched in place. They are deployed with no update or delete path." The keeper contract ships `update` (creator-only, gated on `frozen == 0`) and `freeze` (`smart_contracts/keeper/contract.py:118-147`), and the live TestNet app 769891898 is deployed *unfrozen* by design. The same file reportedly acknowledges the pre-freeze power later (`SECURITY.md:80-83`; reported, not re-verified), so it contradicts itself. Nobody's funds move because of a markdown file, but this is the document a security-conscious user reads before escrowing, and it tells them the one power that *can* reach their escrow doesn't exist. It also guarantees a bad first hour for any outside auditor. Fix before MainNet, not after.

### Medium

**M1 — Rain: the beacon id is accepted unvalidated, once, forever. Confirmed.** `smart_contracts/rain/contract.py:122-133` — `configure` checks `beacon_app > 0` and nothing else. A deployer who points it at a self-controlled `must_get` rigs every draw and takes every pot: participants' money lost to the deployer, permanently (the contract is immutable). A fat-fingered id bricks resolution, and deposited pots have no exit except winner-`claim`. This is a per-community deployment, so the mitigation is participant verification of `beacon_app` global state against the known Foundation ids — which is possible but not surfaced anywhere a participant would actually look. Treat rain as "trust the deployer until you check one global-state value," and say so loudly.

**M2 — Rain: the NFT gate is checked once at entry; tickets are permanent. Confirmed.** `contract.py:200-211` verifies collection membership only at `enter`, and tickets never expire and never leave (no exit method exists). One NFT passed sequentially through N accounts mints N permanent tickets — unbounded dilution of honest holders in a "gated community" draw, and reportedly contradicts `examples/community-rain.md` ("one entry per NFT you hold"; reported line, not re-verified). The code's own comment acknowledges multiple tickets per person as intended, but the NFT-passing version is sharper than "identity is free." **Fix requires new box semantics and, since rain is immutable, a new app id — the expensive category.** Decide whether this is accepted design or a bug *before* anyone runs a real gated draw.

**M3 — Keeper bot: no `max_fee` cap; the bot trusts its algod's suggested fee. Confirmed.** `scripts/keeper_bot.py:514-518` sets only `extra_fee`; the base fee comes from node-suggested params. The documented default endpoint is the public algonode gateway; a compromised or malfunctioning endpoint returning an inflated per-byte fee gets signed away with the next execution. Genesis verification proves the network, not the node's honesty. Confirmed in code; the attack requires a lying endpoint, unlikely but real. One-line fix.

**M4 — `deploy/vps/install.sh` ships the superseded app id as its default. Confirmed.** Line 90 writes `KEEPER_APP_ID=769823086` — the alpha-1 deployment the repo's own docs say must not be used — under a comment explaining the bot has no default precisely because old boxes are a different shape. Every fresh VPS install following the documented path services the wrong registry or crash-loops. No funds at risk; pure readiness rot.

**M5 — The docs teach a dormancy rule the contract doesn't have. Confirmed.** `docs/integrating.md:372-376`: "goes dormant below 12,000, not below 4,000." The code falls back to base fee when escrow can't cover the escalated fee (`smart_contracts/keeper/contract.py:364-366`), so an upkeep is executable while `balance ≥ fee_per_execution`, always. The same wrong rule reportedly sits in `docs/arcron.md` and `specs/keeper/requirements.md:50` (reported; notably `specs/keeper/keeper.spec.md:77` Invariant 12 has it *right*, so the repo disagrees with itself). Effect: creators over-provision or needlessly cancel/re-register; keepers mis-price servable upkeeps.

**M6 — Keeper spec Invariant 18 contradicts the code on ASA-bonus cancel. Confirmed.** `specs/keeper/keeper.spec.md:83` says `cancel` "refuses, before refunding anything" if the creator can't receive the asset. The code zeroes the bonus and pays the ALGO refund anyway (`contract.py:283-286`) — the bonus is forfeited permanently. A creator who trusts the invariant and cancels while not opted in loses the unspent ASA escrow for good. Separately, `specs/keeper/requirements.md` reportedly still describes the pre-#8/pre-#9 contract (one app arg, no ASA fees; reported, not re-verified), so an integrator reading it builds the wrong call shape.

**M7 — Console: no authenticity check on the keeper app id; shareable links point writes at any app. Confirmed.** `web/src/app/core/entry.ts:74-76` accepts any `?app=N`; writes then pay `getApplicationAddress(appId)`. A phishing link to the hosted console with an attacker's lookalike app id gives the victim no console-side signal — no approval-hash pin, and the console reportedly doesn't even read the `frozen` flag it could check for free (reported, not re-verified). Cost: whatever the victim escrows. Related: the TS decoder (`js/src/upkeep.ts:104-117`, reported) drops the tail-offset fingerprint check the Python bot enforces, so pointed at a superseded app's boxes it decodes plausible garbage instead of throwing.

**M8 — Governance: `govern sign` doesn't verify the payload against source. Reported, not re-verified.** Per the governance pass: `scripts/govern.py:219-245` checks only the app id, then prints and signs; the rebuild-and-compare machinery exists but `sign` never calls it, so the entire defense against a compromised coordinator machine is holders manually comparing a hash. Also: the file's network isn't checked against the connected node, and a freeze file — the one irreversible act in the system — arrives to signers as unlabeled hex. Given the 3-of-5 MainNet plan, this is the off-chain component to harden first.

### Low (confirmed unless noted; compressed for breadth)

- **Missing `rekey_to`/`close_remainder_to`/`asset_close_to` asserts on payment/asset gtxns** across rain, subscription, deadman, embargo — and the keeper contract's own `register`/`top_up` (`contract.py:193-210, 240-243`; only receiver and amount are checked). Contract-side loss: none (close/rekey harm the sender). The exposure is a malicious front end slipping poisoned fields into groups users sign — and this project ships a front end. Systemic hygiene gap; mechanical fix.
- **DeadMan:** owner can never withdraw even before firing and beneficiary is immutable — beneficiary key loss strands the escrow; the spec never names this (design trade, undocumented). `claim` needs group fee pooling; the one person who must transact unaided gets a failing txn at ordinary fees.
- **Treasury:** ALGO sent directly to the app address is silently stranded (accounting only credits `deposit`) — the repo's own demo strands ~435k µALGO this way. Recipients that can never claim (app addresses etc.) are accepted at `configure`.
- **Subscription:** one-shot `set_keeper` accepts a nonexistent app id → billing bricked forever (creator self-inflicted; subscriber funds stay withdrawable). No floor on `min_rounds_per_period` beyond `> 0` — a deployer can configure machine-speed billing; transparent parameter, but it's advertised as *the* subscriber protection.
- **Embargo:** `mbr_payment >=` accepts overpayment that is stranded forever, contradicting the spec's "exactly" (`embargo/contract.py:92`); per-instance MBR burn undocumented.
- **Pulse:** `tick_with` notes >119 bytes panic (128-byte global-state limit) — lets a creator register a permanently-failing upkeep; self-inflicted, refundable via cancel.
- **beacon_stub:** no network guard, and both rain demos deploy it on whatever network `--network` selects. Deterministic "randomness" pointed at real value = precomputable winners. Deployment-discipline hazard.
- **Keeper bot:** pays the 1,000 µALGO bonus fee without checking its own opt-in status (bounded loss; the comment at `keeper_bot.py:45-46` is false); backoff state unwritable under the shipped systemd unit (`ProtectSystem=strict`, no `StateDirectory=`); box pagination is dead code that would TypeError if reached; balance guard ignores asset-holding MBR (cosmetic).
- **JS lib:** `execute` helper always pays the bonus fee (Python twin doesn't); `board.ts` misstates keeper net for asset upkeeps by 1,000 µALGO; `register` does zero client-side validation; README's "byte for byte" twin claim overpromises (rejection paths diverge).
- **Web console:** register box-reference races a concurrent registration (fails free, confusing); wrong-chain banner doesn't gate signing; `web/scripts/` live-chain harness is broken (imports paths deleted in the js/ move); ASA-bonus upkeeps registrable but not fundable from the UI.
- **Specs (beyond M6):** keeper spec's exported-state table omits `frozen` — the one flag the whole trust story hangs on; rain's omits `gate_creator`/`prize_asset`; change-log gaps around update/freeze and ASA-bonus commits; watchdog Invariant 4 says repeated checks "change nothing" while incrementing a counter; watchdog's "Not configured" error is unreachable dead code the spec describes as observable.
- **Tests:** the reentrancy spike is broken (stale `RegisterArgs` signature — `scripts/spike_reentrancy.py:59-70` passes `call_data=` and omits required args, so it TypeErrors before any chain call), asserts nothing, and runs in no CI lane; `govern_e2e` only ever updates *empty* apps — "update replaces code, not state" is never demonstrated against an app holding escrow; `multisig_e2e` never freezes; one test asserts `>= 2` inner txns where `== 2` is the real invariant.

### False alarms checked and cleared

- **"Embargo's `schedule` is permissionless and front-runnable"** — claimed by two passes, **wrong**. `smart_contracts/embargo/contract.py:82` asserts `Txn.sender == Global.creator_address`; the comment above it describes exactly this attack. Embargo's real findings are the minor ones listed above.
- **"A malicious target can re-enter `execute` and leak escrow"** — claimed as the consequence of the broken spike. The mechanics are blocked by the AVM rule refusing to re-enter an app already on the call stack (the keeper is mid-execution when the target runs), with the contract's state-before-call ordering as a second line (`contract.py:404-411` before `:421+`) — exactly what `specs/keeper/keeper.spec.md:80` Invariant 15 says. The genuine finding is narrower: the spike that "measured" this is broken and assertion-free, so the claim is currently unbacked by a run.

## 3. Pros — what to keep

- **The keeper contract's defensive engineering is genuinely good.** State written before inner calls; escalation designed against ceiling-farming with a documented failed experiment behind the two-part guard (`contract.py:335-358`); the balance-fallback that turns a permanent freeze into a graceful degradation (`:364-366`); the overflow bound proved from constants rather than asserted from vibes (`:36-43`); the ASA best-effort design that never lets someone else's asset settings hold ALGO hostage (`:280-301`).
- **The "never fail" discipline of the target hooks.** Watchdog's `check_freshness` has no asserts; deadman's `sweep` and treasury's `distribute` return 0 on no-op. A failing target trips keeper backoff and wedges the schedule — the subtlest correctness property of a keeper network, handled correctly and consciously.
- **Measurement culture.** Spike programs for reentrancy, resource limits, multi-arg call shapes, PQ accounts; box decoders pinned to a recorded live box on both the Python and TS sides; the lost-race error-string handling verified down to go-algorand source.
- **Governance design.** `frozen` is public on-chain state; `verify_build` pins bytecode; the multisig tooling refuses Falcon (non-ed25519) accounts; freeze irreversibility is structural, not conventional. The shape is right even where the docs (H2) misdescribe it.
- **Solvency proven, not argued.** An e2e that ends at exact minimum balance and a 1,008-execution soak that came out exactly solvent is the right kind of evidence, and the mock-suite limits that would hide a solvency bug are written down in AGENTS.md instead of discovered later.
- **Candor as a convention.** `docs/design/out-of-scope.md` closing #15/#22 with reasoning; the upgrade path documented as "a real power." When the docs are accurate, they're unusually honest. (When they're not — H2, M5 — it's worse than silence, which is why those rank so high.)

## 4. Cons — what is weak or will bite later

- **Doc/spec drift is systemic, not incidental.** SECURITY.md's headline claim, the dormancy rule in multiple files, stale stage labels, stale superseded-app lists, spec invariants contradicting code, requirements describing a previous version of the contract. `specsync --strict` passes 10/10 because it validates structure, not semantics — the drift lives exactly where the tool can't see.
- **Dead and broken tooling stays in the repo armed.** A reentrancy spike that TypeErrors, a console test harness importing deleted paths, an installer defaulting to a forbidden app id, a systemd unit whose state directory can't be written. Each is small; together they say the non-contract artifacts don't get exercised.
- **The example contracts each carry a silent-stranding trap** (deadman's MBR, treasury's direct payments, rain's ticket MBR, embargo's overpayment). They're documented as examples, but they're shaped like templates, and people will copy them for real money. DeadMan's trap is total and on the default path.
- **Off-chain trust in endpoint honesty.** No `max_fee` anywhere; the bot's profitability is inherited from the contract but its fee safety is inherited from its algod.
- **The immutability story is told ahead of its reality.** "Ownerless," "no admin key," "cannot be patched" — all true only after `freeze`, and the release plan deliberately has third parties escrowing before then.

## 5. Next steps, ranked

1. **Fix SECURITY.md and the dormancy-rule docs** (H2, M5, plus the stale alpha labels). Cheapest, highest-impact; do before any further publicity.
2. **Fix DeadMan** (H1): fund base MBR in `deploy_config.py` and/or reserve it in `arm`/`sweep`; document in the spec. Then fix the other example contracts' stranding traps or label them as intentional burns.
3. **One mechanical sweep adding `rekey_to`/`close_remainder_to`/`asset_close_to` asserts** on every payment/asset gtxn in every contract, keeper included. Rebuild, upgrade-in-place (still possible pre-freeze), redeploy examples.
4. **Fix the keeper ops layer:** `max_fee` in the bot (M3), install.sh app id (M4), systemd `StateDirectory=`, delete or repair the broken spikes and `web/scripts/`.
5. **Decide rain's gated-draw semantics** (M2) and pin beacon-id verification into the console/docs (M1) before promoting any real community draw. M2 is the struct-semantics decision — make it before a rain deployment has users.
6. **Harden `govern sign`** (M8): automatic rebuild-and-compare, network check, loud freeze labeling — before the 3-of-5 is real.
7. **Console:** pin/badge the expected app id per network, surface `frozen`, port the tail-offset fingerprint to the TS decoder (M7).
8. **Close the test gaps that matter:** update-with-escrow-then-execute across the boundary; multisig freeze; re-run the (fixed) reentrancy spike against the deployed bytecode; tighten the `>= 2` inner-txn assertion.
9. **Then freeze the MainNet deployment** — and only then write "ownerless" anywhere.

## 6. Confidence rating

**For the keeper contract itself, post-freeze, with docs fixed: 7/10.** For the **whole system as it stands today: 5/10** — dragged down not by the core but by H1's live trap in a shipped example, H2/M5/M6's wrong trust documentation, and the unexercised governance-against-escrow path.

To raise it: (a) `freeze()` executed on the MainNet deployment, with `verify_build` run against the on-chain programs; (b) the doc/spec corrections above; (c) the fixed reentrancy spike actually run against the deployed bytecode; (d) an e2e stage proving update-with-escrow works across the boundary; (e) someone other than the author running the e2e and soak clean.

The single thing most likely to be wrong that was **not** checked: **that the deployed bytecode of app 769891898 actually corresponds to the reviewed source.** OnComplete routing was verified in the compiled TEAL of several *example* contracts and embargo was recompiled byte-identically, but nobody fully recompiled `keeper` and diffed it against the live app's programs. Everything said about the keeper contract is a statement about the source; the source↔chain equivalence is asserted by repo tooling (`verify_build`) that was read about but not run.

## 7. The direct question

**Would I escrow my own money in this on MainNet today? No.** Two specific reasons, both fixable: the deployment would still be unfrozen while SECURITY.md misdescribes that power, and the deployed bytecode was not verified against the reviewed source. After freeze + a bytecode verification + the documentation corrections: **yes for the keeper contract itself**, in amounts scaled to "one independent review, no paid audit" — the core logic is the strongest part of this repository and the solvency evidence is real. For the example targets, **no**: deadman has a total-loss trap on its default path, and rain requires trusting a deployer-set beacon id that nothing helps participants verify. They're demos; treat them as demos until H1/M1/M2 are resolved.
