# J2 acceptance criteria: a creator registers their first upkeep

Converted from the prose criteria in `docs/journeys.md` (lines 61 to 96),
grounded in `web/src/app/components/register-form.ts`,
`web/src/app/core/keeper.service.ts`, `web/src/app/core/arcron.service.ts`,
`js/src/keeper-txns.ts`, `js/src/upkeep.ts` and
`smart_contracts/keeper/contract.py` at `main` (`69fdbab`).

**How to read this.** Each scenario is meant to be pass or fail by one person
sitting in front of the console with a funded TestNet account, without
consulting the source. Where a scenario cannot pass on `main` today there is a
`# Today:` line naming what actually happens, with a file and a line. Absence
of a `# Today:` line means the behaviour exists and the scenario is a
regression guard, not new work.

Three numbers recur and are worth stating once, verified against the code:

- At the form's own defaults (`tick()uint64`, no arguments, funding
  0.012 ALGO) the box MBR is **62,100 microALGO** and the funding is
  **12,000 microALGO**, so the tile reads **0.0741 ALGO**.
- `register` builds a three transaction group (`js/src/keeper-txns.ts:104` to
  `143`) on unmodified suggested params, so each leg pays its own minimum fee:
  **3,000 microALGO** more.
- The debit is therefore **0.0771 ALGO** against a quote of **0.0741 ALGO**.
  The tile is short by exactly the group's own fees, every time, on every
  configuration of the form.

## A. Registering without a contract of your own

This is the blocker. The form opens on "Target app id"
(`register-form.ts:49-51`) with a control defaulted to `0` and validated
`min(1)` (`register-form.ts:187`), while the method signature next to it
defaults to `tick()uint64` (`register-form.ts:188`,
`js/src/keeper-abi.ts:40`), which is the demo target's hook. The form is
nearly configured to demo itself and then asks for the one value it never
offers. Neither `js/src/networks.ts` nor anything under `web/src` contains the
pulse app id; it exists only in prose (`docs/status.md:25`, `README.md:14`,
`docs/arcron.md:11`).

```
Scenario: Somebody with no deployed contract can complete a registration
  Given a connected account with enough ALGO
  And the user has never deployed an Algorand application
  When they open the register panel
  Then there is a way to proceed that does not require them to know or type an app id
  And taking it produces a registration they can complete without leaving the console
  # Today: impossible. The first field is a required app id with no default
  # (register-form.ts:187) and nothing on the page names a target they could
  # use. The button stays disabled on Validators.min(1).
```

```
Scenario: The demo target is offered by name, not implied by a default signature
  Given the register panel with nothing filled in
  When the user reads the panel top to bottom
  Then a demo target is offered explicitly, with what it is and what calling it does
  And the offer states that it is a demo and that the call has no effect on anything they own
  And the offer names the target's app id and links it to a block explorer
  # Today: the only trace of the demo target is the default in the signature
  # field, "tick()uint64" (register-form.ts:188). The word "pulse" appears
  # nowhere in web/src or js/src except that constant's name.
```

```
Scenario: Choosing the demo target fills in every field it determines
  Given the register panel
  When the user chooses the demo target
  Then the target app id and the method signature are both filled in
  And the arguments field is either absent or shows that this call takes none
  And the "Up-front cost" figure updates in the same interaction
  And the user can still change any of it afterwards
```

```
Scenario: The panel explains what a target is before asking for one
  Given a user who does not know what "target app id" means
  When they read the label and its helper text
  Then they learn that a target is a contract Arcron will call, that they fix
      what is called and a keeper only chooses when
  And they learn that they may use the demo target instead of supplying one
  # Today: "Target app id" has a number input and no helper text at all
  # (register-form.ts:48-51). The panel subtitle (register-form.ts:37-43)
  # explains fee ceilings before it explains what is being called.
```

```
Scenario: A target app id that does not exist is refused before the wallet opens
  Given the register panel with a target app id that is not an application on this chain
  When every other field is valid
  Then the submit control is disabled
  And the reason names the app id and says no application with that id exists on this network
  # Today: the console never looks the target up, and the contract does not
  # check it either: register asserts nothing about target_app
  # (smart_contracts/keeper/contract.py:171-238). The console's only guard is
  # Validators.min(1). Whatever the node does with the reference, an upkeep
  # registered against a target that cannot be called escrows money, occupies
  # a paid box, and can never execute; the escrow comes back only by cancel.
```

```
Scenario: A signature the target does not expose is refused before the wallet opens
  Given a target app id that exists
  And a method signature the target does not implement
  When every other field is valid
  Then the submit control is disabled
  And the reason says the target does not expose that method
  # Today: the signature is only parsed for encoding (register-form.ts:253-267).
  # It is never checked against the target. A typo in the signature registers
  # fine and produces an upkeep whose every execution fails.
```

```
Scenario: A target that rejects the call is refused before the wallet opens
  Given a target app id and signature that exist
  And the target's hook fails when called by the keeper application
  When the user attempts to register
  Then the failure is surfaced before the wallet opens, quoting what the target said
  And the panel says that an upkeep whose target rejects is never serviced,
      and that recovering the escrow means cancelling
  # Today: nothing simulates the resulting execution. js/src/keeper-txns.ts:294
  # already does exactly this technique for `execute` (empty signer,
  # allowEmptySignatures, allowUnnamedResources), so the machinery exists and
  # the register path does not use it.
```

```
Scenario: The panel does not pretend a demo registration is production
  Given the user registered against the demo target
  When the registration confirms
  Then the console says plainly that this upkeep calls a demo contract and does nothing else
  And it points at how to hook up a contract of their own
```

## B. Asked in their terms

`docs/journeys.md:71` asks for the user to be questioned about what they want
to happen and how often, with contract fields assembled behind that. The form
today is nine controls in registration order, not in intent order:
target app, signature, arguments, bonus asset id, bonus per run, interval,
fee per execution, fee ceiling, funding, plus a policy fieldset
(`register-form.ts:47-128`).

```
Scenario: The first two questions are what should happen and how often
  Given the register panel
  When the user reads it top to bottom
  Then the first thing asked is what call should be made
  And the second is how often
  And nothing before those two asks for a fee, a ceiling, an asset or a policy
  # Today: field four is "Bonus asset id (optional)" (register-form.ts:67-71),
  # which is an ASA fee capability that CLAUDE.md records as deliberately not
  # wired in. It sits above the cadence question.
```

```
Scenario: Cadence is asked as time and stored as rounds
  Given the interval field
  When the user sets any interval
  Then the field shows the equivalent in human time, the seconds per round used,
      and whether that rate was measured or assumed
  And a set of quick cadence choices sets the interval from a time, not a round count
  # Preserve: register-form.ts:293-298 and 372-375 do this correctly today,
  # including saying "measured" versus "nominal". Do not lose the basis word:
  # on LocalNet the rate is never measured (arcron.service.ts:116) and a
  # confident "every 28 s" would be a lie there.
```

```
Scenario: The ASA bonus is not part of a first registration
  Given a first time creator
  When they complete the panel without making any choice about assets
  Then no asset field has been presented to them
  And the upkeep they register pays its keeper in ALGO
  # Today: two of the nine fields are ASA bonus fields, and the console has no
  # UI at all for the two calls that make a bonus work. KeeperService.optInAsset
  # and topUpAsset exist (keeper.service.ts:52-69) and nothing in web/src calls

  # bonus can never be funded from this console, having also committed to a
  # further 0.1 ALGO opt-in that is permanent and non-refundable
  # (contract.py ASSET_OPT_IN_MBR, js/src/upkeep.ts:28) and appears in no quote.
```

## C. The cost panel

`docs/journeys.md:73`: "The cost shown is the cost charged." Today
`upFront()` is box MBR plus funding (`register-form.ts:347-351`) and the
group's three fees are not in it.

```
Scenario: The quoted total is the amount debited
  Given the register panel at its defaults
  When the user reads the up-front cost
  Then the figure equals the total microALGO that will leave their account if they sign
  And after signing, the difference in their balance matches that figure
  # Today: quotes 0.0741 ALGO, debits 0.0771 ALGO. The 0.003 gap is the three
  # minimum fees of the group built at js/src/keeper-txns.ts:104-143, which
  # passes unmodified suggested params to all three legs.
```

```
Scenario: The total is broken down into named parts
  Given the register panel with a valid configuration
  When the user reads the cost panel
  Then it shows, as separate labelled lines that sum to the total:
      the box deposit, the escrow funding, and the network fees for this group
  And each line states whether it comes back and when
  And the total is shown as a total, not as one of the parts
  # Preserve and extend: the "refunded in full on cancel" note on the box MBR
  # (register-form.ts:353-357) is correct against contract.py cancel, which
  # returns escrow plus released box MBR. Keep that sentence. The escrow line
  # needs the equivalent: spent one fee at a time, refundable on cancel.
  # The fee line needs the opposite: gone either way, including on a failure.
```

```
Scenario: The network fee component is read from the network, not assumed
  Given the register panel
  When the cost panel shows the fee component
  Then that number came from the node's suggested parameters for this group
  And if the node's minimum fee is not what the console assumed, the shown

```

```
Scenario: The quote is restated at the moment of signing
  Given a cost panel the user has read
  When they submit
  Then the group actually built is priced at the same figure that was on screen
  And if the node's parameters have changed so that it is not, they are shown
      the new figure and asked again rather than being sent to the wallet
  # Today: suggested params are fetched inside register() at
  # js/src/keeper-txns.ts:103, after the click, and the tile is never
  # reconciled against them.
```

```
Scenario: The cost panel tracks every field that moves it
  Given the register panel
  When the user changes the signature, the arguments or the funding
  Then the up-front figure changes in the same interaction
  # Preserve: register-form.ts:342-351 recomputes from the encoded args, so
  # arguments correctly change the box price. This is right and easy to lose.
```

```
Scenario: A configuration that cannot be priced says so instead of showing a number
  Given a signature that will not parse
  When the user looks at the cost panel
  Then it shows no figure and says the signature has to be fixed before the box can be priced
  # Preserve: register-form.ts:349 and 355 do exactly this ("-", plus
  # "fix the signature to price the box").
```

```
Scenario: Costs that follow from a choice are quoted with that choice
  Given the user has set a bonus asset
  When they read the cost panel
  Then it also shows the 0.1 ALGO asset opt-in, that it is permanent and never refunded,
```

## F. What the cross-field validation already does, and must keep doing

`docs/journeys.md:76`: every rejection the contract could give is a disabled
control with a specific reason. This is the strongest part of the current
form (`register-form.ts:200` to `350`) and the section most at risk from a
redesign. These scenarios are regression guards. Every one of them passes on
`main` today.

```
Scenario: A fee ceiling below the fee is refused in the form
  Given a fee per execution of 0.01 ALGO
  When the user sets a fee ceiling of 0.005 ALGO
  Then the submit control is disabled
  And the reason says a ceiling must be at least the fee per execution, or zero for no escalation
  # Preserve: register-form.ts:215 and 316. Mirrors contract.py:179.
```

```
Scenario: Funding below one worst-case execution is refused in the form
  Given a fee per execution of 0.004 ALGO and a ceiling of 0.02 ALGO
  When the user sets funding to 0.01 ALGO
  Then the submit control is disabled
  And the reason names 0.02 ALGO as the price this upkeep can be charged for one execution
  # Preserve: register-form.ts:218 and 323-327. Mirrors contract.py:236-238.
  # The point is that it prices against the ceiling and not the headline fee,
  # which is the whole reason the check is non-obvious.
```

```
Scenario: A bonus asset with no bonus is refused in the form
  Given a bonus asset id above zero
  When the bonus per run is zero
  Then the submit control is disabled
  And the reason says to set a bonus per run, or set the asset id to zero to drop it
  # Preserve: register-form.ts:221 and 318-320. Mirrors contract.py:183.
```

```
Scenario: An interval below the contract's minimum is refused in the form
  Given the interval field
  When the user enters fewer than 10 rounds
  Then the submit control is disabled
  And the field says what the minimum is
  # Preserve: register-form.ts:192-195 and 295. Mirrors contract.py:171.
```

```
Scenario: A fee below the contract's minimum is refused in the form
  Given the fee per execution field
  When the user enters less than 0.004 ALGO
  Then the submit control is disabled
  And the field states the minimum and that keepers spend about 0.003 in group fees
  # Preserve: register-form.ts:196-199 and 90. Mirrors contract.py:173.
  # Keep the second half of that sentence: it is the only place the console
  # explains why the floor is where it is.
```

```
Scenario: An argument that will not encode names the argument and the reason
  Given a signature declaring arguments
  When the user types a value that will not encode as its declared type
  Then the submit control is disabled
  And the message names which argument, its ABI type, and what was wrong with the value
  # Preserve: register-form.ts:253-267 and 321-322, feeding on
  # js/src/keeper-abi.ts:50-93. Encoding at validation time rather than at
  # submit time is what makes this a disabled button instead of a rejection.
```

```
Scenario: Too many app args for one execution is refused in the form
  Given a signature with three or more arguments
  When the selector plus arguments exceeds three app args
  Then the submit control is disabled
  And the message states the count built and the limit, counting the selector
  # Preserve: register-form.ts:258-262. Mirrors contract.py:188.
```

```
Scenario: A failing chain read disables the submit control
  Given the register panel with a valid configuration
  When the last read of the app failed
  Then the submit control is disabled
  # Preserve: register-form.ts:365-369, with its comment. This is the guard

  # trust warning on the page is unrendered. registry-table.ts:273 has the

```

```
Scenario: A disabled control always says why
  Given any configuration that will not submit
  When the user looks below the submit control
  Then there is a sentence naming the specific problem, not a generic one
  And "connect an account" is distinguished from a validation failure

```

```
Scenario: The runway figure is priced at what the upkeep can actually be charged
  Given a fee per execution of 0.004 ALGO, a ceiling of 0.02 ALGO and funding of 0.1 ALGO
  When the user reads the funding field's helper text
  Then it reports 5 runs, not 25
  And it says the count is at the ceiling
```

```
Scenario: A fee ceiling is described as a price to expect, not a worst case to hope against
```

```
Scenario: The catch-up policy is described by consequence, not by name

  And the choice is explicit rather than inherited from a default the user never saw
```

## G. Signing, and everything that can go wrong around it

```
Scenario: The registration is simulated before the wallet opens
  Given a valid configuration and a connected account
  When the user submits
  Then the group is simulated first
  And if the simulation fails, the wallet never opens and the reason is shown on the page
  # Today: register goes straight to the wallet (keeper.service.ts:37-42 into
  # js/src/keeper-txns.ts:96-145). The execute path does simulate first
  # (js/src/keeper-txns.ts:294-319) and docs/journeys.md:143 records fixing
  # exactly this for keepers. Register did not get the same treatment, and it
  # is the path that commits the larger sum.
```

```
Scenario: Declining in the wallet leaves the form as it was
  Given the wallet prompt open
  When the user declines
  Then the console says the signature was declined, not that something failed
  And every field the user filled in is still there
  And the submit control is live again
  # Today: the decline is caught (keeper.service.ts:122-125), rendered by
  # describe() as whatever the wallet's error string is, and shown in the
  # activity panel as a red alert (activity-log.ts:15-20). The form does keep
  # its values. Note that WalletService already distinguishes a dismissal from
  # a failure (wallet.service.ts:21-29) and KeeperService does not use it.
```

```
Scenario: The wallet disconnecting mid flow does not leave the panel looking ready
  Given the wallet prompt open, or a submission in flight
  When the wallet session drops
  Then the submit control returns to its disconnected state with the connect prompt
  And any figure that depended on the connected account is cleared rather than left stale
```

```
Scenario: A wallet set to a different network is caught before signing
  Given the console on TestNet
  And the connected wallet set to another network
  When the user submits
  Then the mismatch is reported by the console, naming both networks
  And the console does not present the wallet's own error as the whole story
  # Today: WalletService keeps one manager per console network
  # (wallet.service.ts:125-137) and nothing compares the wallet's active
  # network to arcron.network(). The user sees whatever the wallet says.
```

```
Scenario: Another registration landing first does not cost the user a rejected group
  Given the user has a registration ready to sign
  And another account registers an upkeep on the same app in the meantime
  When the user signs
  Then either the group succeeds, or the console explains that the registry moved and offers to rebuild it
  And the user is not shown a raw box reference error
  # Today: nextUpkeepId is read while the group is built
  # (js/src/keeper-txns.ts:142) and the box reference it produces is stale the
  # moment anyone else registers. The contract writes the box at the id it
  # holds (contract.py:240-241), which is now unreferenced, and the call
  # fails. The user pays nothing but sees an unexplained failure, and the
  # window is the whole time the wallet prompt is open. Simulating
  # immediately before submission (see the first scenario in this section)
  # closes most of it; retrying once on this specific failure closes the rest.
```

```
Scenario: The node going down between the quote and the signature is survivable
  Given a quote on screen
  When the node becomes unreachable before the user signs
  Then the submit control is disabled before the wallet can open
  And the reason says the console cannot currently read the chain
  # Partly today: canSubmit gates on arcron.status() (register-form.ts:369),
  # which turns to 'error' within one 2.5 second poll
  # (arcron.service.ts:18 and 224-228). The gap is a submission already past
  # the button: register() fetches suggested params and next_upkeep_id after
  # the click (js/src/keeper-txns.ts:103 and 142) and a failure there produces
  # a raw network error.
```

```
Scenario: Submitting twice does not send two registrations
  Given a submission in flight
  When the user clicks submit again
  Then nothing further is sent
  # Preserve: keeper.service.ts:114 sets busy, register-form.ts:364 gates on
  # it, and the label changes to "Registering..." (register-form.ts:141).
```

```
Scenario: The wallet is never asked to sign anything the page did not describe
  Given the wallet prompt open for a registration
  When the user reads the three transactions
  Then each is one the page has already named: the box deposit, the escrow funding, and the app call
  And the amounts match the lines in the cost panel
  # The group's two payments carry distinguishing notes, "arcron:mbr" and
  # "arcron:funding" (js/src/keeper-txns.ts:112-121). Those strings are the
  # only labels a wallet can show and the console explains neither.
```

## H. After signing

`docs/journeys.md:75`: "After signing they see their upkeep, and can watch it
execute for the first time without hunting for it."

```
Scenario: The new upkeep is identified and reachable from the confirmation
  Given a registration that confirmed
  When the user reads the confirmation
  Then it names the upkeep's id, the round it landed in, and its transaction
  And there is a control that takes them to that upkeep
  # Partly today: the activity entry says "Registered upkeep <id>" with round
  # and txId (keeper.service.ts:40, activity-log.ts:25-33), and the registry
```

## Decisions the maintainer has to make

**1. What does a first-time user register, and against what?**
Either the console ships the pulse app ids per network (a `demoTarget` beside
`defaultAppId` in `js/src/networks.ts`) and offers "call the demo target" as a
first-class choice, or J2 is redefined to begin after the user has deployed
something and the console links out to `docs/integrating.md` instead. Shipping
pulse makes J2 completable in one sitting and makes the console demo itself,
at the cost of a second published app id per network that has to be kept
alive, funded and correct, and of every first-time registration pointing at
a contract that does nothing the user cares about. Redefining J2 keeps the
console honest about what it is for, and concedes that the first journey we
build cannot be completed by the audience it names.

**2. If the demo target ships, is the demo registration real money?**
Either the demo path is an ordinary registration at ordinary cost (about
0.077 ALGO on TestNet, refundable on cancel except the fees), or it is
presented as a rehearsal with the numbers shown and no signature required
until the user opts into the real thing. The first proves the whole path
including the wallet; the second lets somebody understand the product before
they are asked for anything, which is what J1 demands one journey earlier.

**3. Who executes the first run?**
Either the console gives the creator an explicit "run it now" control on their
new upkeep (the machinery exists: `KeeperService.execute` and the registry's
Execute button, and at the minimum fee the creator roughly breaks even), or
the first run waits for the network and the console tells the user honestly
that TestNet is serviced every thirty minutes. The first makes J2's "watch it
execute" true within seconds and slightly muddles the story that keepers are
other people; the second keeps the story clean and means the journey's last
step routinely takes half an hour.

**4. Does the console simulate `register` before the wallet opens?**
Either it does, which turns the stale `next_upkeep_id` race, insufficient
balance, the app account's own MBR, and every remaining contract assert into
one pre-signature refusal for the price of one extra round trip and a hard
dependency on the node being up at click time; or it does not, and each of
those is handled by a separate check with its own failure mode. Simulation is
strictly more correct and strictly less legible: the message the user sees on
a failure is the AVM's, not ours. Note that `execute` already made this
choice in the affirmative (`js/src/keeper-txns.ts:294`).

**5. How is the fee component quoted?**
Either the cost panel shows one total that includes the group's fees, which is
what "the cost shown is the cost charged" literally asks for and which can go
stale between quote and signature if the network's minimum fee moves; or it
shows escrow and deposit as one figure and network fees as a separate line
described as set by the network. One number is what a person wants; two
numbers are what stays true. Both beat today, where the fees are absent.

**6. Balance: hard block or warn?**
Either an account that cannot afford the total disables the submit control,
which means a stale or failed balance read blocks a registration that would
have succeeded; or it shows a warning and lets the user proceed, which keeps
the raw network rejection reachable and concedes part of
`docs/journeys.md:74`. This is the same trade-off `canSubmit`'s existing
`status() === 'ready'` guard already resolved in favour of blocking, so
consistency argues for blocking.

**7. Do the ASA bonus fields stay in the first-registration form?**
Either they are removed from this panel and moved behind an advanced path,
which matches CLAUDE.md's position that ASA fees are a capability rather than
a commitment and removes two of nine fields from a first-time creator's way;
or they stay and the console grows UI for `opt_in_asset` and `top_up_asset`,
without which a bonus set here can never be funded from the console at all.
The one thing that cannot stay is the present state, where the field is
offered and the follow-up is unreachable.

**8. What ends J2: a confirmation, or a place?**
Either J2 ends at a good confirmation (upkeep id, explorer links, expected
first run, a scroll to the highlighted row), which is buildable now and leaves
the "mine" filter and the per-upkeep page to J3; or J2 ends by landing the
user on their upkeep's own page, which pulls the first slice of J3 forward and
makes J2 considerably larger. The `Upkeep` struct already carries `creator`
(`js/src/upkeep.ts:38`) and `board.ts` already computes most of a detail page,
so the second is cheaper than it looks, and it is the only version where "see
their upkeep, and watch it execute without hunting for it" is unambiguously
true.

**9. Wrong chain: block or warn?**
Either a genesis mismatch is promoted to a hard block on every write path
(the smallest fix is one clause in `canSubmit`), or it stays a banner. It is
currently a banner over a live button, which is the worst of both. There is no
real argument for the second option, so this is more a confirmation than a
choice, but it changes `arcron.status()`'s meaning and so is worth stating.
