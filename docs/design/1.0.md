# What 1.0 is

Decided 2026-08-24. This is the scope of the last struct-changing deployment,
what is deliberately out, and what has to happen before mainnet.

The shape of the plan comes from one hard constraint: **the keeper contract
cannot be upgraded.** Changing the `Upkeep` struct means a new app id and an
empty registry, and every creator must cancel and re-register by hand because
`cancel` is creator-only. So struct changes are batched into one release and
then the surface is frozen.

## In

| Issue | What | Why it is in 1.0 |
|-------|------|------------------|
| [#7](https://github.com/CorvidLabs/archon/issues/7) | Per-upkeep catch-up policy | Two of the three shipped demos behave *wrongly* after any outage without it — `rain` and `deadman` want SKIP_AHEAD, `treasury` wants CATCH_UP. A protocol constant is wrong for someone whichever way it is set. |
| [#14](https://github.com/CorvidLabs/archon/issues/14) | Overdue fee escalation | Without it, minimum-fee upkeeps are second-class and their creators cannot fix that except by cancelling and re-registering higher. Escalation is what makes a small user's upkeep reliable at all. |
| [#8](https://github.com/CorvidLabs/archon/issues/8) | Resource declaration | [#24](https://github.com/CorvidLabs/archon/issues/24) measured that keeper-supplied references already reach two levels down; the capability exists and only *discovery* is missing. Without it, targets can never pay an arbitrary account, call a DEX, or read a balance. |
| [#9](https://github.com/CorvidLabs/archon/issues/9) | ASA fee **capability** | Fees denominated in any ASA. Not because CORVID is being used — it is not — but because this is the last redeployment, and adding it later would mean another one. |

## Out, deliberately

**CORVID is not wired in.** 1.0 supports ASA-denominated fees; it does not
require, prefer or default to any particular asset. Escrow and fees are ALGO
unless a creator chooses otherwise. "No token required" stays true.

**[#15](https://github.com/CorvidLabs/archon/issues/15) staking and assignment
windows** — out. It changes the core value proposition and needs review before
any code, and 1.0 is meant to be a surface we can freeze and self-review.

**[#22](https://github.com/CorvidLabs/archon/issues/22) keeper-supplied call
data** — out. It is a decision about what Arcron *is*, not a feature. Note the
tension with #8: declaring which *resources* a call may touch is safe, because
the creator still fixes what is called; letting a keeper supply *data* is a
different thing entirely, and 1.0 does the first and not the second.

## Sequence

1. **Design #8 and #9** to the standard of [`scheduling-and-fees.md`](scheduling-and-fees.md)
   — measured constraints, options with costs, open questions. The batching
   decision cannot be made without them.
2. **Review all four designs together.** They share a struct; the field budget,
   the box MBR and the migration are one conversation, not four.
3. **Implement as one change.** Contract and spec first, then both decoders and
   both pinned box vectors in the same commit, then the bot's selection logic,
   then the console, then the e2e cases. `fledge lanes run local` green
   throughout.
4. **Deploy once.** New app id, docs repointed, the old app deprecated with a
   migration note — the procedure from
   [#3](https://github.com/CorvidLabs/archon/issues/3), which is written down
   and has been done once.
5. **Dogfood on TestNet** (below), with a keeper and the notifier running.
6. **Self-review against [#12](https://github.com/CorvidLabs/archon/issues/12)**
   while it soaks.
7. **Go public** when the first impression is a deployment we are not about to
   replace. The licence, security policy and contributor docs land before that
   ([#50](https://github.com/CorvidLabs/archon/pull/50)); only visibility waits.

## The dogfood

**A recurring treasury distribution on TestNet, serviced by a keeper we run and
watched by the notifier.**

Chosen over a heartbeat or a one-shot settlement for three reasons:

- **It exercises the 1.0 feature we are building.** The treasury is the demo
  that *needs* CATCH_UP — every period's deposits must be distributed, and
  skipping silently loses a week of allocations. Dogfooding it tests #7 rather
  than working around it.
- **Its failures are legible.** Money-shaped accounting means a missed or
  duplicated distribution shows up as a number that is wrong, not as an absence
  nobody notices. A heartbeat that stops looks exactly like a heartbeat nobody
  is watching.
- **It runs forever.** The mainnet gate is *time on TestNet*, and time only
  counts if something is actually running for it. A one-shot settlement fires
  once and proves nothing about sustained operation.

Operationally it is low-risk: TestNet ALGO, an escrow we top up, and the
notifier announcing failures to a channel. If it breaks, we find out from the
thing that is supposed to tell us — which is itself the test.

## The mainnet gate

No paid audit. Mainnet is gated on:

- the 1.0 contract **unchanged** for a sustained period — any struct change
  restarts the clock, which is the point of freezing the surface;
- the dogfood upkeep **serviced continuously** over that period, with the
  notifier's record as evidence;
- [#12](https://github.com/CorvidLabs/archon/issues/12) completed as a rigorous
  self-audit: invariants enumerated and tested, threat model written, known
  limitations stated, every claim in the docs checked against a chain rather
  than against memory.

`SECURITY.md` says plainly that this code is unaudited, and that does not
change by deploying it to mainnet. What changes is that we will have watched it
work, under a contract that cannot be quietly altered underneath anyone.
