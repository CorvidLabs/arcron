## 1. Manufactured lateness — could not refute the extraction, did refute the limits

**Path.** `execute` (`contract.py` 390–400): if `fee_cap > fee_per_execution` and `due > last_serviced_round`,

```
lateness = round - last_serviced
excess   = min(max(lateness - interval, 0), interval)
fee      = base + (cap - base) * excess // interval
```

then the inner call to the target, then `itxn.Payment` to `Txn.sender`. A rejected inner call reverts the group; the keeper pays 0 (confirmed: `exhaust_budget` and `refuse` both left the attacker’s balance unchanged). `resource_probe.guarded` asserts `round >= next_allowed` and then sets `next_allowed = round + gap`. Anyone can call it.

**Worked example, same numbers as the spike, reproduced.** Base 4,000, cap 40,000, interval 10, gap 6.

| step | result |
|---|---|
| honest `execute` at first due | creator paid **7,600** (LocalNet: the execute txn is itself a block, so every run is one round late; excess=1, extra 3,600) |
| attacker `guarded()` | costs 1,000 |
| honest `execute` | refused, honest paid **0** |
| attacker `execute` once the window reopens | creator paid **25,600** (excess=6) |
| attacker wallet | **+21,600** (25,600 − 1,000 − 3,000 execute fee) |

`poetry run python -m scripts.spike_hostile_target --network localnet` asserts this and exited 0. 25,600 − 4,000 = 21,600 more than base; 21,600 / 1,000 = 21.6×, which they rounded to 22×.

**Economics.** LocalNet hides concurrent keepers: the spike’s honest account tries once, then the attacker waits alone. That would overstate profit if honest keepers retried every round. **The reference bot does the opposite.** `scripts/keeper_backoff.py` treats an inner-tx failure as a broken target, not a lost race (`INNER_FAILURE_MARKER = "inner tx"`). First failure backs off `1 × interval` rounds, capped at 1,286 (~one hour). `select_due` then **omits** that upkeep, and the comment says a rising fee does not fix a broken target. Against `keeper_bot`:

- 10-round interval → silent for 10 rounds; gap is 6; attacker has the window alone
- daily upkeep → silent for an hour

There is no race to win. 21,600 is a lower bound against this client, not an overestimate. I could not construct a case where the attack loses money except “the attacker fails to submit `execute` at all,” which is not a market constraint.

TestNet 2.8 s/round does not save this. The attacker knows `next_allowed` and can sit `first_valid` on that round. Custom keepers that do not back off would split the prize; the bot this repo tells people to run will not be in that split.

**Severity.** Agree it is not a contract-theft bug: every µALGO is inside the `fee_cap` the creator stored, `cancel` still works, CATCH_UP still pays base on replays. Disagree that it is merely advice.

Escalation’s premise — lateness means the job did not clear at base — is false whenever the target can be shut. That is an incentive bug in the feature `#14` just added. `fee_cap = 0` is a workaround that means “do not use the feature.” There is **no method that changes `fee_cap` after `register`**, so the seven live escalating upkeeps cannot take the advice without cancelling and re-registering. The console already defaults the ceiling to 0 and already says “expect to pay it”; `docs/integrating.md` was not updated on this branch.

**Remedy.** `fee_cap = 0` on a blockable target stops the extra payment. It does not stop the liveness half: one inner-tx failure still sends `keeper_bot` away for up to an hour, including on upkeeps with escalation off.

The ramp claim is true. The one-interval ramp is only in `execute` (390–400). The box stores `fee_cap`, `fee_per_execution`, `interval_rounds`, `last_serviced_round`, `policy` — not the formula. `update` can stretch it; `freeze` locks it. Spreading the ramp does **less** than they think, because the reference bot will not “get through once” inside the backoff. A slower ramp cuts the payout per hit; it does not force the attacker to keep paying 1,000 while honest keepers retry.

**Measured** (fresh probe, gap 15, interval 10, SKIP_AHEAD): cycle 0 honest 7,600; cycles 1–5 attacker **22,000** each (excess = 5; `4000 + 36000×5/10`). Five cycles, no extra `guarded()` calls.

Their spike used `GUARD_GAP = 6 < INTERVAL = 10`, which is the only configuration in which that sentence holds.

This is exactly the “oracle once an epoch / rebalancer once an epoch” target they used as the motivating example, pointed at an upkeep whose interval is shorter than that epoch.

### 2c. Sibling upkeep as the blocking call — +30,800, and it bypasses “restrict to the keeper app”

**Measured:** sibling paid the attacker **4,000**; honest victim refused; victim paid **32,800**; wallet **+30,800**. The blocking transaction is an earning `execute`, not a 1,000 µALGO app call.

## 4. The diff, as a diff

**`scripts/node_retry.py` — POST retry.** The CDN story is not a sound general argument. `is_refusal` matches any 403/429. algosdk’s `algod_request` raises `AlgodHTTPError(message, code)` and **drops headers**; a Nodely quota 403 and an auth-proxy 403 are indistinguishable. Wrapping is installed on every `connect()`, including LocalNet and any `ALGOD_SERVER`.

The implementation is still safe for duplicate submit, for a reason they did not use: `install` wraps `algod_request`, and `send_raw_transaction` POSTs the already-signed `txn_bytes`. A retry is the same blob. Algorand txn ids are hashes; a second POST is “already in the pool” / “already committed,” not a second payment. That is why POST is safe here, not “the CDN never forwarded it.”

Excluding 5xx is a product choice, not a safety requirement at this layer. A 502 on GET is safe to retry; a 502 on POST of the same blob is too. `retry_after_seconds` looking at `error.headers` is dead against real algosdk errors. The 1-in-15,000 figure is `0.09^4`; the code does five attempts (`0.09^5 ≈ 1 in 169,000`).

**`read_escrowed(..., 1.0, 0)`.** Sound. Those arguments only feed `runway_days` and `rounds_late`, which the sum does not read. Fragile if a later caller uses the `UpkeepHealth` list for anything else. Pagination, above, is the real hole.

**`govern status` solvency line.** Right place. `create` cannot fund an address that does not exist yet. Process still exits 0 on shortfall, which is fine for a status command. The sample `54.201` in `deploying.md` is a snapshot; the audit’s `54.217` is an earlier one. Both can be true hours apart.

**`test_the_fallback_to_base_is_the_keepers_to_decline`.** Proves: escrow below the escalated fee → `execute` pays base; after a **separate** `top_up` of `cap - held`, `execute` pays cap and the box is 0. Does not prove a same-group atomic top-up (a sniper can take a non-grouped top-up). Does not prove 19,400. The last assert is `cap - shortfall == held` with `shortfall = cap - held`, which cannot fail. The 19,400 figure is LocalNet-only and lives in a docstring.

**`spike_hostile_target` in `[lanes.local]`.** It is deterministic enough to stay green, because it **does not assert the finding**. If `guarded` does not hold, or the attacker never gets through, or the three-execute group is refused, the function returns an empty `escapes` and the process exits 0. `measure_atomic_backlog` never asserts `runs == 3`. A lane that “must stay green” will, including when the attack has stopped working. That is the opposite of `keeper_race`, which they correctly left out of the lane because a non-collision proves nothing.
