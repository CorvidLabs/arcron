**The worse version exists, it was measured, and it does not self-heal.** The verification's §3 limits ("it needs to win the race at reopen", "it self-heals within two cycles", "extraction, not capture") hold only for a target whose gate reopens by itself. Against a target whose gate a third party can move *both* ways — an oracle whose "pause" anyone can set and clear, a rebalancer with a public `set_epoch`, anything with an unpermissioned toggle like `resource_probe.set_gap` on this very branch — the attacker never races anything. Call path: attacker sends `[target.close]` once; every honest `execute` (contract.py:409-430, the inner `ApplicationCall`) fails inside the target at cost 0; when `Global.round - last_serviced_round ≥ 2·interval` the attacker sends one atomic group `[target.open, keeper.execute, target.close]`. Nobody else ever observes the target open. Measured on LocalNet (hand-written TEAL target, `/tmp/arcron_review/spike_toggle.py`, run as `PYTHONPATH=$PWD poetry run python /tmp/arcron_review/spike_toggle.py --network localnet`), base 4,000, cap 40,000, interval 10, three cycles = 60 rounds:

- SKIP_AHEAD: creator paid **120,000** where the honest schedule costs 24,000, and got 3 executions instead of 6. Attacker net **+104,000** (3 × 40,000 less 3 × 5,000 in group fees less the 1,000 opening close). Honest keeper net 0 after three blocked attempts.
- CATCH_UP: creator paid **132,000** (each cycle 40,000 at cap plus the 4,000 replay the attacker also takes, same group shape). Attacker net **+101,000**. Six executions, all by the attacker.

Per cycle the attacker's outlay is 5,000 (open 1,000 + execute 3,000 + close 1,000) against `cap − base`; it is profitable for any gap above 5,000, and it continues for as long as the attacker keeps the close inside the group, which costs nothing extra. The "self-heals" sentence is true only after the attacker chooses to stop. The creator's escrow drains at 5× to 5.5× the rate they budgeted, bounded — as the document says — by the cap they chose, which is the same bound the verification already accepted for I1.

**Our own keepers hand the reopen to the attacker, so the one-way race limit does not bind either.** The refusal text algod returns for a blocked execute is `logic eval error: inner tx 0 failed: logic eval error: assert failed pc=…`. `scripts/keeper_backoff.is_lost_race` (line 62) returns **False** for anything containing `inner tx` (marker at line 59), so `record_failure` grows the wait: `min(2^(failures−1), 8) × interval`, capped at 1,286 rounds (lines 163-164). On a 10-round interval that is 10, 20, 40, 80 rounds; on the live 6-hour cadences it is ~1 hour per retry. The GitHub cron keeper (`.github/workflows/keeper-bot.yml`, `*/30 * * * *`) starts fresh each run with no memory and polls every ~640 blocks. An attacker watching each 2.8 s block takes the reopen round; a keeper that checks once per 640 blocks or once per hour after the first refusal is not in the race. Verify: `poetry run python -c "from scripts.keeper_backoff import is_lost_race; print(is_lost_race('logic eval error: inner tx 0 failed: logic eval error: assert failed pc=69'))"` → `False`. This is a design choice that is right for a genuinely broken target and exactly wrong here; the document does not mention it and the "race at reopen" reassurance in §3 assumes the opposite.

**The spike's target shape is the one that does not pay on the live registry; the shape that pays is not modelled.** The spike's guard blocks two calls within 6 rounds on a 10-round interval, so one 1,000 close holds the window for 60% of an interval. On a 6-hour (~7,700-round) interval the same short-cooldown target would need ~1,300 closes (1.3 ALGO) to hold one interval closed against an 8,000-10,000 gap: a loss. What pays at real cadences is an epoch-style one-way target (gate ≈ interval: one close per cycle, attacker takes the reopen round against keepers that are not watching) and any two-way target (above). The "22x return on 1,000" is gap/interval = 0.6 doing the work; on the attacker's full 4,000 outlay it is 5.4x, and the marginal gain over the 7,600 an honest winner earned is 18,000. Not wrong, but it is the least representative number in the document and the README repeats it as the headline.

**The ramp claim is right; the ramp remedy is not, and there is a better `update`-reachable one.** Confirmed: `contract.py:390-407` computes `excess = min(max(lateness − interval, 0), interval)` and `fee = base + (cap − base)·excess // interval` from box fields base/cap/interval; the ramp's *shape* is program, reachable by `update`, closed by `freeze`. But spreading it over k intervals only forces a one-way attacker to re-close k times (k × 1,000 against an 8,000+ gap still pays for k ≤ 7) and does nothing against a two-way attacker whose close is already in every group. Note also the overflow bound: `(cap − base)·excess` fits uint64 only while `excess ≤ 18·interval`-ish for a cap of 10¹⁸, so k ≤ 18. The remedy that actually removes the incentive without a struct change is to stop paying for lateness the keeper set can be made to create: either keep the default at 0 (the console already defaults `feeCap` to 0 — `web/src/app/components/register-form.ts:489` — and `docs/integrating.md:410-445` already tells creators to leave it there, for the lone-keeper reason; the verification cites neither) or replace automatic escalation with a creator-signed `raise_fee(upkeep_id, fee) ≤ fee_cap`, so the bid comes from the party who is paying and who can see whether the target is really unserviceable. That fits in `update`, touches no box layout, and is what I would decide before `freeze`. The document's last paragraph reaches the right ordering conclusion for a weaker reason.
